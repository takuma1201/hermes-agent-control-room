## Ollama bound to localhost (2026-10-03)

Root cause: Ollama.app stores an `expose` flag in
`~/Library/Application Support/Ollama/db.sqlite`, table `settings`, column `expose`. It was `1`.
The parent app then **overrides** `OLLAMA_HOST` for its child `ollama serve` process, so
`launchctl setenv OLLAMA_HOST 127.0.0.1` alone did NOT work: the parent had `127.0.0.1`
while the child still received `0.0.0.0` (confirmed with `ps -E`).

Fix: quit Ollama, `UPDATE settings SET expose=0;`, relaunch.
Backup: `~/workspace/backups/ollama-localhost-20261003-000129/` (db.sqlite.before, config.json,
server.json, com.electron.ollama.plist).
Restore: quit Ollama, `UPDATE settings SET expose=1;` (or copy db.sqlite.before back), relaunch.

Verified: listens `127.0.0.1:11434`; child env `OLLAMA_HOST=127.0.0.1`; `/api/tags`
local = 200, LAN IP = no connection, Tailscale IP = no connection.
No client impact: OpenClaw references `http://127.0.0.1:11434`.

## Weekly backup scheduled (2026-10-03)

Previously there was NO backup job at all (`hermes cron list` = 0 jobs,
`~/.hermes/backups/` held only `config`).

Job `c2b544598675` "Weekly Hermes Backup", `0 4 * * 0`, `--no-agent` (no LLM),
script `~/.hermes/scripts/weekly-backup.sh`, delivery `local`.
Output: `~/workspace/backups/hermes-auto/hermes-backup-<stamp>.zip`, mode 600, keeps 4.

The script verifies the archive with `unzip -tqq` and fails loudly if the file is missing
or corrupt. Pitfall found: `hermes backup -q` does NOT write the `-o` zip — it writes a state
snapshot to `~/.hermes/state-snapshots/` instead. The script must call `hermes backup -o` with
no `-q`.

Verified: manual run and `hermes cron run c2b544598675` both succeeded;
8434 files, 442 MB, integrity check passed.

**The archive contains secrets (`.env`, `auth.json`). Keep it local; never commit or sync it.**
